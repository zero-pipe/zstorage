# ZCS 各协议延时实测（2026-11-24）

> 目的：摸清 ZCS 自身的延时与首屏能力，作为网页播放器 / 桌面客户端适配的依据。
> 验收口径：首屏 ≤2s 可接受，>3s 无竞争力。

## 1. 测量方法

- **测试流**：ffmpeg 推 960×540\@25fps、GOP=1s 的亮度时钟画面（16/89/162/235 四档每秒一换），
  播放端解码后按亮度跳变对齐推流端媒体时间轴，差值即端到端延时。
- **首屏**：从发起拉流到解码出第一帧的墙钟时间。
- **WebRTC**：无头 Edge + CDP 驱动真实浏览器（`/index/api/webrtc?...type=play`，ICE → DTLS → SRTP），
  用 `requestVideoFrameCallback` 取每帧时刻与亮度，因此**包含了浏览器自身的抖动缓冲**，是最贴近用户的一条。
- **两处系统性误差**：
  1. 端到端延时以推流端 `-progress` 的 `out_time_us` 为基准，该值按块落盘，含滞后；
     已用「多点采样取最小滞后」估计偏移，残余误差约 ±0.1s；
  2. 不含「摄像机 → ZCS 拉流（AddStreamProxy）」这一段，现网会再叠加。
- **首屏必须压小探测窗口再看**：默认 ffmpeg 参数下 RTMP 首屏会从 0.25s 虚高到 1.38s，
  多出来的全是 demuxer 预缓冲，不是 ZCS 的锅。

## 2. 首屏（秒）

| 协议 | 中位 | 区间 | 说明 |
|---|---|---|---|
| **WebRTC** | **0.32** | 0.30–0.69 | 浏览器实测，含页面加载 + SDP/ICE 协商 |
| HTTP-FLV | 0.10 | 0.08–0.37 | 从 GOP 缓存回放，最快 |
| HLS | 0.11 | 0.10–0.16 | 首片立即可读，但画面是 1~2s 前的 |
| RTMP | 0.25 | 0.11–0.39 | 与 FLV 同路径，多一次握手 |
| RTSP-UDP | 0.83 | 0.64–1.26 | DESCRIBE/SETUP/PLAY + 时钟 pacing |
| RTSP-TCP | 0.87 | 0.67–1.21 | 同上 |

## 3. 稳态端到端延时（秒）

| 协议 | 中位 | 区间 | 备注 |
|---|---|---|---|
| **WebRTC** | **0.06** | 0.02–0.37 | 最优；个别轮次 0.35s，取稳定区间 0.05–0.15 |
| HTTP-FLV | 0.44 | 0.38–0.51 | 起播 0.7s 内收敛到稳定值 |
| RTMP | 0.49 | 0.46–0.53 | 同上 |
| RTSP-TCP | 0.73 | 0.69–0.77 | 比 FLV 多 ~0.25s，见 §5 |
| HLS | 1.8 | 1.1–2.2（最差 3.2） | seg_dur=2，画面在新旧切片间反复跳 |

**收敛特性**：所有直播协议都从最近的关键帧开始回放 GOP 缓存（`zcs_gop_reader_seek_gop_key`），
首屏那帧必定"稍旧"，实测 0.7s 内追上直播；GOP 缓存深度 `gop_target_gops=3`。

## 4. 能力现状

### 4.1 本机 ZCS 没有编译 WebRTC / SRT

`build/CMakeCache.txt`：`ZCS_ENABLE_WEBRTC=OFF`、`ZCS_ENABLE_SRT=OFF`，而 `conf/config.ini` 里
`[webrtc] enable=1`、`[protocol] enable_srt=1`——配置写了但不生效（启动日志只提示一句）。
**要验 WebRTC 必须另编**：`cmake -DZCS_ENABLE_WEBRTC=ON -DZCS_ENABLE_SRT=ON`，
并保证 `externIP` 是本机真实 IP，否则 ICE 候选打空、连接必失败。

### 4.2 WebRTC 通路正常（曾误判）

用近乎全静止的亮度图案测试时出现「收得到 RTP 但 `framesReceived=0`、浏览器反复发 PLI」，
平均每包仅 21 字节。核对后**不是回归**：同一图案在上一版本（379e356）行为完全一致。
换成有运动的画面立刻正常：

| 画面 | 码率 | 收包 | 解码帧 | 关键帧 |
|---|---|---|---|---|
| 高熵运动（testsrc2 叠加） | 1.3 Mbps | 2283 | 198 | 8 |
| 近静止 + 轻微噪声 | 84 KB/s | 1900 | 204 | 9 |
| **逐像素完全相同** | ~4.7 KB/s | 1900+ | **0** | **0** |

结论：只有"帧与帧完全一致"这种退化输入会让 WebRTC 出不了帧（编码器不产 VCL，服务端发的是近空包），
同一路流的 FLV/RTSP 不受影响。真实摄像机有传感器噪声，不会命中；但**录播回放 / 纯色测试画面**要留意。

### 4.3 SRT 播放被拒

推 SRT 正常（`SRT publish start`），播 SRT 一律
`SRT play unavailable: app=live stream=xxx`——`zcs_media_source_use_gop_queue_play()` 返回 false。

### 4.4 附带发现

- `conf/config.ini` 的 `externIP=192.168.1.4`，本机实际是 192.168.1.2。WebRTC 的 ICE 候选直接打到
  一个不存在的地址，ICE 必然失败。**现网部署也要注意这个值。**
- 平台 `mediaurl.BuildWebRTCURLs` 无条件下发 `rtc`/`rtcs`，不看节点 `EnableWebRTC`；
  前端 `playerStrategy.js` 又是"有 rtc 字段就当可用"。节点没开 WebRTC 时，「超低延迟」会被选中然后必然失败。

## 5. 可调项

| 项 | 位置 | 现状 | 影响 |
|---|---|---|---|
| `[rtsp] low_latency` | ZCS `conf/config.ini` | `0`（按播放时钟 pacing） | RTSP 那多出来的 ~0.25s 就在这 |
| `gop_target_gops` / `gop_cache_sec` | ZCS | 3 / 5 | 首屏回放深度 |
| `[hls] seg_dur` | ZCS | 2 | HLS 延时的下限 |
| 播放器缓冲 | 网页 `jessibuca.vue` `videoBuffer:0.2` | — | 网页端剩余延时主要在这 |
| mpv 缓存 | zplayer `mpv_media_player.cpp` | 未设置（默认 `demuxer-readahead-secs=1`） | 桌面端会再加 ~1s |

## 6. 结论

1. **ZCS 自身够快**：WebRTC ~0.06s、FLV/RTMP ~0.45s、RTSP ~0.7s，首屏全部 <1s。瓶颈不在流媒体内核。
2. **WebRTC 是唯一能进"极致"档的协议**：比 FLV 快近一个数量级，且首屏 0.3s。
   前提是节点真的编译了 WebRTC——本机这版没有。
3. **网页端默认走 FLV 是合理的**（兼容性/音频最稳），但「超低延迟」一旦可用就是真差距，
   值得把「节点是否具备 WebRTC」如实上报，别让用户选到一个注定失败的选项。
4. **桌面端最亏**：走 RTSP（多 0.25s）+ libmpv 默认缓存（多 ~1s），改完能直接从 2s 级拉到 0.5s 级。
5. **HLS 只作兼容兜底**：1.1–2.2s，已经踩到 2s 线。

## 7. 复现环境

- 对照实例：`build-rtc/`（`-DZCS_ENABLE_WEBRTC=ON -DZCS_ENABLE_SRT=ON`），
  配置 `build-rtc/test.ini`（RTMP 11935 / RTSP 18554 / HTTP 18081 / SRT 19000），不干扰 8080 上的正式实例。
- 浏览器探针：`rtcprobe/probe.html` + `run.mjs`（无头 Edge + CDP，取 `getStats()` 与逐帧亮度）。
